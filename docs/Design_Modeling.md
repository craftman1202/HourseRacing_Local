# 地方競馬 予測モデル ローカル開発 設計書 v1.0

## 1. 設計原則

将来のGCP移行を「コードの書き換えなし」で済ませるため、ストレージ抽象化を最初から入れます。具体的には、パスを `fsspec` 互換のURI文字列で扱い、環境変数 `DATA_ROOT` に `file:///home/user/nar-data` を入れるか `gs://nar-data` を入れるかだけで切り替わるようにします。ディレクトリ階層は前回のGCP設計と完全に同一にし、移行時は `gcloud storage rsync -r` 一発で終わる状態を維持します。

再ダウンロードを永久に不要にする方針は、**原本ZIPをバイト列のまま不変（immutable）に保存し、そこから下流をすべて再生成可能にする**ことです。パース仕様やスキーマ定義を変更しても、NARへの再アクセスは一切発生しません。原本を消してよいのは、NARの仕様変更で列構成が変わり、かつ過去分の再取得が可能だと確認できた場合のみです。

## 3. データ取得

### 3.1 対象と物量

月次レース情報は1998年1月から現在まで、2026年8月時点で344か月です。月次オッズ情報は2026年3月以降のみで6か月、かつ10日区切りの3分割なので18ファイルです。合計 344 + 18 = 362リクエスト。3秒間隔なら初回バックフィルは約20分で完了します。

```python
RACE_URL = "https://www.keiba.go.jp/KeibaWeb/DataDownload/RaceDataDownload"
ODDS_URL = "https://www.keiba.go.jp/KeibaWeb/DataDownload/OddsDataDownload"
# monthly: params = {"type": "monthly", "k_year": 2026, "k_month": 7}
# daily  : params = {"type": "daily"}
```

### 3.2 ダウンロード台帳

`manifest.duckdb` に1レコード1ファイルで記録します。

```sql
CREATE TABLE manifest (
  file_key      VARCHAR PRIMARY KEY,  -- 'monthly/race/2026-07'
  url           VARCHAR,
  params_json   VARCHAR,
  fetched_at    TIMESTAMP,
  http_status   INTEGER,
  content_length BIGINT,
  sha256        VARCHAR,              -- ZIPバイト列のハッシュ
  raw_path      VARCHAR,
  inner_files   VARCHAR,              -- ZIP内のCSV名リスト
  schema_hash   VARCHAR,              -- 全CSVのヘッダー列名を連結してハッシュ
  status        VARCHAR,              -- ok / schema_drift / parse_error
  is_final      BOOLEAN               -- 確定済み＝再取得不要
);
```

`is_final` の判定ルールが再ダウンロード回避の中核です。**当該月の月末から45日以上経過していて、かつ直近の取得で `sha256` が前回と一致した月次ファイル**を最終確定とみなし、以後は取得対象から外します。45日という余裕を取るのは、着順の事後訂正（降着・失格の裁決変更）や賞金訂正が数週間後に反映されることがあるためです。

更新チェックは `is_final=false` の月だけを対象に、日次で当月と前月のみ再取得します。344か月を毎回叩く必要はありません。

```python
def should_fetch(key, ym, today):
    rec = manifest.get(key)
    if rec is None or rec.status != "ok":
        return True
    if rec.is_final:
        return False
    return ym >= (today - relativedelta(days=45)).strftime("%Y-%m")
```

### 3.3 取得実装の要点

HTTPクライアントは `httpx` を使い、`User-Agent` に用途と連絡先メールを明記します。リトライは 429/500/502/503/504 に対して指数バックオフ（初回2秒、係数2、ジッタ±30%、最大5回）。レスポンスの `Content-Type` が `application/zip` でなければエラー扱いにします（HTMLのエラーページが200で返る可能性があるため）。リクエスト間隔は最低3秒のトークンバケットで強制します。

ZIPは受信後すぐにSHA-256を計算し、既存の同キーレコードとハッシュが一致すればディスク書き込みごとスキップします。書き込みはテンポラリファイルに書いてから `os.replace` でアトミックに移動し、中断時に壊れたZIPが残らないようにします。

デコードは `cp932` を第一候補、失敗時に `utf-8-sig`、それも失敗なら `cp932` の `errors="replace"` でログに警告を出しつつ通します。1998年前後の古いファイルには外字や機種依存文字が混入している可能性があるので、ここで止めないことが重要です。

### 3.4 スキーマガード

NARは仕様を予告なく変更すると明記しているため、ZIP内の各CSVについてヘッダー行（実際にはヘッダー無しCSVの可能性があるので、列数と1行目のパターン）から `schema_hash` を計算し、`meta/schema_hash.json` の既知値と比較します。不一致なら `status='schema_drift'` を立てて **silver層への昇格を停止し、処理を止めます**。壊れたデータを黙って取り込むのが最悪の失敗なので、ここは fail-fast にします。

期待値は仕様書ベースで、レース一覧66列、出馬表36列、オッズ10列、払戻54列です。

## 4. 正規化とキー設計

### 4.1 主キー

`race_id` は `競馬場コード(2桁) + 競走年月日(8桁) + レース番号(2桁)` の12桁文字列とします。競馬場名（「大井」）から数値コード（20）への変換マスタは、月別開催日程ページの `k_babaCode` パラメータを全月ぶんスクレイプして自動生成し、ハードコードを避けます。ばんえいの「帯広ば」と平地の表記差異、名称変更（「荒尾」など廃止場を含む）に対応するため、マスタは名称の完全一致辞書＋未知名称でのエラー停止とします。

**馬の同定が最大の難所です。** 出馬表には馬IDがなく `馬名` しかありません。地方競馬では改名や同名馬が実際に存在します。そこで代理キーとして `馬名 + 生年月日 + 父馬名` のハッシュを `horse_sk` とし、さらに「同一 `(生年月日, 父馬名, 母馬名)` で馬名が異なるレコード群」を改名候補として検出し、時系列で連結する名寄せテーブル `horse_alias` を別途生成します。母父馬名も一致すればほぼ確実に同一馬です。この名寄せの品質が過去成績特徴量の精度を直接決めるので、EDAで必ず検証してください。

騎手・調教師も同名対策として `氏名 + 所属` を代理キーにしますが、移籍で所属が変わるため、`氏名` 単位のキーと `氏名+所属` 単位の両方を保持し、特徴量では前者を主に使います。

### 4.2 払戻テーブルの縦持ち化

54列の横持ちは扱いが苦痛なので、`(race_id, bet_type, comb_1, comb_2, comb_3, payout_yen, popularity, dead_heat_seq)` の縦持ちに変換します。同着で複数行になる仕様は `dead_heat_seq` で吸収します。オッズテーブルも既に縦持ち構造なので、両者が同じ形になり、収支照合が単純なJOINで済みます。

## 5. 【重要】リーク構造の分析と pre-race スキーマ

ここが本設計で最も注意を要する部分です。

出馬表CSVには、明らかにレース後の情報である `着順`、`タイム`、`着差`、`上がり3F`、`人気` が含まれます。これらは無条件に破棄します。問題は**その他の列にも時点の疑わしいものがある**ことです。

具体的に危険なのは `騎手成績`（例: `1-1-0-1`）、`全成績`（`10-1-3-16`）、`ダート左成績`、`ダート右成績`、`当競馬場成績`、`うち当距離成績`、`最高タイム`、`最高タイム良馬場` の8列です。月次ファイルは毎晩再生成されるため、**これらの累積成績が「当該レース発走時点」ではなく「ファイル生成時点」の値である可能性が高い**のです。もしそうなら、1998年のレース行に2026年時点の通算成績が入っていることになり、これは未来情報の直接的な混入です。

検証手順を必ず実行してください。同一レースについて、月次ファイルの複数世代のスナップショット（当日ファイルと、その後の月次ファイル）で当該列を比較します。値が変化していれば as-of-download 確定です。加えて、ある馬の連続する出走をトレースし、`全成績` の合計が出走回数と整合しているか（レースを重ねるごとに単調増加するか）を確認します。単調増加せず全行同一値なら、その列は使えません。

**設計上の結論として、これら8列は原則すべて破棄し、自前の履歴から as-of 集計で再計算します。** 検証で as-of-race であることが確定した列だけを、明示的なホワイトリストで復活させます。破棄しても情報は失われません。1998年からの全レース結果を持っているので、同じ集計を自分で正確に作れます。

`pre-race` スキーマは実装で強制します。

```python
POST_RACE_COLS = frozenset({
    "着順","タイム","着差","上がり3F","人気",
    "騎手成績","全成績","ダート左成績","ダート右成績",
    "当競馬場成績","うち当距離成績","最高タイム","最高タイム良馬場",
})
# レース一覧側も同様
POST_RACE_RACE_COLS = frozenset(
    {"上がり4F","上がり3F"} |
    {f"ハロンタイム{i}" for i in range(1,16)} |
    {f"コーナー名称{i}" for i in range(1,9)} |
    {f"コーナー通過順{i}" for i in range(1,9)} |
    {"頭数"}   # 出走取消・除外の反映時点が不明なため除外側に置く
)

def to_prerace(df: pl.DataFrame) -> pl.DataFrame:
    drop = [c for c in df.columns if c in POST_RACE_COLS | POST_RACE_RACE_COLS]
    return df.drop(drop)
```

`天候` と `馬場` は発走前に確定する情報なので使用可能ですが、**発表が発走直前**であり、かつ月次ファイルの値はレース後の最終値です。運用時は当日ファイルから取る必要があるため、学習では使うが「運用時に取得できるか」をフラグ管理します。同様に `馬体重` は前検日または当日発表なので使用可、`ハロンタイム` から派生する馬場高速度指数は当日の先行レースぶんだけ使う、という時点制御が必要です。

`頭数` を除外側に置いたのは、出走取消や競走除外が反映された最終頭数である可能性があるためです。代わりに出馬表の行数から自前でカウントします。

## 6. 特徴量設計

すべての履歴系特徴量は「当該レースの発走時刻より厳密に前」のレコードのみから計算します。DuckDBのウィンドウ関数で `ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING` を使い、同日同場の先行レースは発走時刻順で順序付けます。

```sql
-- as-of 集計の基本形（馬の過去成績）
SELECT
  race_id, horse_sk,
  COUNT(*)  OVER w                          AS h_starts_prior,
  SUM(is_win) OVER w                        AS h_wins_prior,
  AVG(is_win) OVER w                        AS h_winrate_prior,
  AVG(speed_index) OVER (PARTITION BY horse_sk
        ORDER BY start_ts ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING) AS h_si_last3,
  DATE_DIFF('day', LAG(race_date) OVER w2, race_date) AS h_days_since_prev
FROM entry_result
WINDOW w  AS (PARTITION BY horse_sk ORDER BY start_ts ROWS UNBOUNDED PRECEDING EXCLUDE CURRENT ROW),
       w2 AS (PARTITION BY horse_sk ORDER BY start_ts);
```

特徴量群は7カテゴリで構成します。馬の履歴（出走間隔、距離別・馬場状態別・競馬場別の勝率と連対率、自己ベスト相対タイム、直近3走の速度指数トレンド、前後半3Fタイム差〔ペースバランス〕のas-of平均による脚質傾向、クラス昇降履歴、初出走フラグ）、騎手（as-of の勝率をベイズ収縮したもの、当該競馬場での勝率、当該馬との過去コンビ成績、乗り替わりフラグ）、調教師と厩舎（同様の収縮勝率、所属場と開催場の一致）、騎手×調教師（直近2年の組み合わせ成績をWilsonスコア信頼区間下限で評価した相乗勝率）、血統（父・母父の種牡馬別ダート適性を階層ベイズで収縮した推定値、インブリード指標は母父までしかないので限定的）、レース条件（距離、回り、クラス、賞金額の対数、頭数、枠番と馬番の相対位置、想定隊列）、競馬場バイアス（場×距離×枠番の過去勝率を収縮、逃げ有利度を先行レースのラップから推定）、市場情報（トラックBのみ：単勝オッズ、複勝オッズ、市場暗黙確率の対数オッズ、締切前オッズの変化率）。

ペースバランスと騎手×調教師の相乗勝率は `docs/Research.md` のレビュー（§13.1）で追加した項目です。前後半3Fタイム差は当該レースそのものについては§5でPOST_RACE_RACE_COLSとして破棄していますが、これは「対象レースの結果」だからです。馬の**過去走**のハロンタイムは対象レース発走時点で既に確定済みの情報なので、as-of集計の入力として使って構いません。ここを混同しないよう、実装では「当該レース行から算出する特徴量」と「過去走を集計する特徴量」でモジュールを分離します。

速度指数は自作が必要です。`タイム` と `距離` から基準タイムを引き、その日の同場同距離の平均タイムで馬場差を補正した標準化残差を使います。地方は場ごとのコース形態差が極端なので、この補正がないと場をまたいだ比較が成立しません。

騎手・種牡馬などのカテゴリは出走数が極端に偏るため、生の勝率ではなく経験ベイズ収縮 `(wins + α·p̄) / (starts + α)` を使います。`α` はハイパーパラメータとしてHPOに含めます。カテゴリのエンコーディングは、GBDT系はネイティブカテゴリ扱い、DL系とロジット系は out-of-fold ターゲットエンコーディング（fold内でのみ統計を計算しリークを防ぐ）とします。

**ばんえい（帯広）は別競技なので、データセットから完全に分離します。** 距離200m、そりの積載重量という別次元の変数があり、同一モデルに混ぜると両方が劣化します。門別も他場と質が異なりますが平地なので、場ダミーで吸収を試み、EDAで残差を確認します。

## 7. EDA

EDAは「モデルを作る前に必ず答えを出しておく質問リスト」として実行します。

第一に、時系列カバレッジと欠損の地図です。年×競馬場のヒートマップで、レース数、出馬表の行数欠損率、タイム欠損率、払戻欠損率を可視化します。NARが「過去のレース情報には欠損がある」と明記しているので、どの年から使えるかをここで決めます。経験的には2000年代前半に馬体重や血統の欠損が多いと予想されるため、**学習の主対象を2010年以降**とし、それ以前は種牡馬事前分布の推定にのみ使う、という二段構えを想定しています。

第二に、前節のリーク検証です。累積成績8列の時点性の確定は、EDAの最優先項目です。

第三に、名寄せの検証です。`horse_sk` ごとの出走間隔分布に異常（同日重複出走、20年超の現役期間）がないか、`horse_alias` で連結した馬の年齢が連続しているかを確認します。

第四に、ターゲットの基礎統計です。頭数分布、枠番別勝率（場ごと）、人気別勝率と単勝オッズの較正曲線（favourite-longshot bias の確認。地方でこのバイアスがどの程度あるかは市場効率性の指標そのものです）、上位人気の勝率が市場暗黙確率とどれだけ乖離するかを場別・クラス別に見ます。

第五に、分布シフトの検出です。年ごとの特徴量分布のPSI（Population Stability Index）を計算し、コロナ期の無観客開催、名古屋の新コース移転（2022年）、笠松の開催自粛期間といった構造変化点を特定します。これがwalk-forward分割の設計に直接影響します。

第六に、控除率の実測です。券種別に「払戻総額 ÷ 投票総額」を払戻金とオッズから逆算し、単勝80%、複勝80%、馬連75%といった公称値と一致するかを場別に確認します。主催者ごとに設定が違うので、期待値計算で使う控除率は実測値ベースにします。

## 8. モデル選定と実装

各パラダイムから1つずつ選定しました。選定理由も添えます。

### 8.1 古典統計：正則化付き条件付きロジット（McFadden discrete choice）

競馬予測における1980年代以来の標準手法で、Silvermanの正則化＋frailty拡張が改良版として知られています。レース内で確率の総和が1になる構造を仮定に組み込むため、競馬の「1レース1勝者」という制約と数学的に整合します。実装は各レースを1つの選択集合とみなす層別条件付き尤度で、L1/L2正則化とレース単位の frailty（ランダム効果）を入れます。`statsmodels` の条件付きロジットでは正則化が弱いので、JAXで対数尤度を直接書き、L-BFGSで最適化する自前実装を推奨します。頭数が可変なのでパディングとマスクで処理します。

$$P(i \text{ wins race } r) = \frac{\exp(\mathbf{x}_i^\top \beta)}{\sum_{j \in r} \exp(\mathbf{x}_j^\top \beta)}$$

解釈可能性が高く、他モデルのサニティチェックの基準線になります。これが他を上回るなら、特徴量エンジニアリング以外の複雑さは不要という判断ができます。

### 8.2 機械学習：LightGBM LambdaRank

TabArena（NeurIPS 2025）を含む近年のベンチマークでは、十分なHPO予算を与えた場合でもGBDTが表形式データで支配的という結論が繰り返し確認されています。競馬はレース単位のグルーピングが本質なので、二値分類ではなく `lambdarank` 目的関数を使い、`group` にレースの頭数を渡します。ラベルは「1着=3、2着=2、3着=1、その他=0」の段階付けにして、勝ち馬だけでなく上位入着の情報も学習に使います。この段階数・重み付けは固定値とせずHPO対象に含め、`docs/Research.md`（§2.2）が提案する5段階グレード（1着=5〜6着以下=0）も探索空間に加えます。NARはJRAより少頭数開催が多いため、段階を増やすと少頭数レースで信号が疎になり過学習を招く懸念があり、どちらが優れるかは検証で決めます（詳細は§13.1）。

LambdaRankの出力はスコアで確率ではないため、レース内softmaxで正規化したうえで、後段のキャリブレーション（後述）を必ず通します。比較用に `binary` 目的＋レース内正規化も同一パイプラインで走らせ、どちらが優れるかをHPOの選択肢に含めます。

### 8.3 深層学習：TabM（ICLR 2025）＋ listwise 損失

表形式DLの現行SOTAとされるアーキテクチャで、パラメータ効率的アンサンブル（1つのMLPが複数のMLPのアンサンブルを模倣する）により、少ない計算量でDeep Ensemble相当の性能とキャリブレーション改善を得ます。本件では損失を、レース単位のsoftmax交差エントロピー（= Plackett-Luceの1位項）に置き換えます。頭数可変への対応はマスク付きsoftmaxです。

TabPFN v2も検討しましたが、推奨データサイズの上限（バージョンにより数千〜数十万行、特徴量数も制約）に対して本件は数百万行あり、素直な適用が不適です。ただし「特定の場×距離のような小サブセットでの専門家モデル」としては有望なので、将来の拡張候補として設計上のフックだけ残します。

DL側の副次的な価値は埋め込み表現です。馬・騎手・種牡馬のエンティティ埋め込みを学習させ、それを他モデルの特徴量として供給する経路も試します。

### 8.4 ベイズ統計：階層ベイズ動的 Plackett-Luce

各馬の潜在能力 $\theta_{h,t}$ を状態空間モデル（ランダムウォーク）で時変にし、レース結果の順位を Plackett-Luce 尤度で観測モデルとします。騎手効果・調教師効果・種牡馬効果を階層事前分布で部分プーリングし、出走数の少ない個体を全体平均へ自動収縮させます。

$$\theta_{h,t} = \theta_{h,t-1} + \epsilon,\quad \epsilon \sim N(0,\sigma_h^2), \qquad
\mu_{i} = \theta_{h(i),t} + \gamma_{j(i)} + \delta_{s(i)} + \mathbf{z}_i^\top \beta$$

実装は NumPyro + NUTS（GPU利用可）とします。全期間フルNUTSは現実的でないため、直近数年をNUTSで推定し、それ以前を経験ベイズで事前分布に圧縮する方式、または全期間をSVI（AutoNormal ガイド）で近似し、最終窓のみNUTSで検証する二段構えにします。「計算量を気にしない」方針でも、MCMCの収束診断（R-hat < 1.01、ESS > 400、発散遷移ゼロ）は必ず確認し、通らないモデルは採用しません。

ベイズ手法の最大の利点は予測の不確実性が事後分布から直接得られることで、これが後述のKelly資金配分で実質的な価値を持ちます。

### 8.5 アンサンブル

4モデルのレース内正規化済み確率を入力に、レース単位softmaxの制約付きスタッキングを行います。メタ学習器は非負重み和1制約付きのロジット空間線形結合（幾何平均型ブレンド）とし、重みは walk-forward の out-of-fold 予測のみから推定します。ここで訓練内予測を混ぜると重みが致命的にバイアスするので、OOF厳守です。

$$\log \pi_i \propto \sum_{m=1}^{4} w_m \log p_i^{(m)}, \quad w_m \ge 0,\ \textstyle\sum w_m = 1$$

比較対象として単純平均、対数平均、そして特徴量条件付きゲーティング（頭数やクラスで重みを変える混合エキスパート）も評価します。

## 9. 検証設計

### 9.1 walk-forward 5-fold と OOS

時系列を purged walk-forward で分割します。学習期間は拡張窓（expanding）を主、固定窓（rolling）を副として両方評価します。

| fold | train | gap | validation |
|---|---|---|---|
| 1 | 2010-01 〜 2018-12 | 30日 | 2019-02 〜 2019-12 |
| 2 | 2010-01 〜 2019-12 | 30日 | 2020-02 〜 2020-12 |
| 3 | 2010-01 〜 2020-12 | 30日 | 2021-02 〜 2021-12 |
| 4 | 2010-01 〜 2021-12 | 30日 | 2022-02 〜 2022-12 |
| 5 | 2010-01 〜 2022-12 | 30日 | 2023-02 〜 2023-12 |
| **OOS** | 2010-01 〜 2023-12 | 30日 | **2024-02 〜 現在** |

30日のギャップ（embargo）を挟むのは、履歴系特徴量が学習期間末尾の情報を含むためです。ローリング勝率の窓長が最大180日なら、embargo も180日に合わせるのが厳密です。この設計上、**embargo長は特徴量の最大ルックバック窓に等しくする**というルールを実装で強制します（`conf/cv.yaml` に窓長を宣言し、embargoを自動導出）。

分割の単位はレースであり、同一レースが train と valid に分かれることは絶対に禁止します（同一レース内の馬は結果が相互依存するため）。さらに同一開催日をまたがせないことも保証します。

OOS期間は最終評価に一度だけ使い、HPOや特徴量選択には一切触れません。ここを覗いた時点で全評価が無効になるので、OOSデータへのアクセスをコードレベルでロックし、`--unlock-oos` フラグ付きの最終評価スクリプトからのみ読めるようにします。

### 9.2 HPO

nested構成にします。外側が上記5-fold、内側は各foldの学習期間をさらに時系列分割した3-foldで、Optuna（TPESampler + MedianPruner）により探索します。目的関数は5-fold平均のレース内負の対数尤度（NLL）です。NLLを主指標にするのは、後段の期待値計算が確率の較正精度に直接依存するためで、Top-1精度やNDCGでは較正が改善しません。

探索回数はLightGBMが500試行、TabMが300試行、条件付きロジットが100試行（正則化強度と収縮パラメータのみ）、ベイズは事前分布のスケールを50試行程度とします。試行数はモデル間で公平になるよう、探索空間の次元数に応じて調整します（TabArenaの知見どおり、DL側に十分な予算を与えないとGBDT有利のバイアスがかかります）。

### 9.3 特徴量選択

3段構成にします。第1段は Null Importance によるスクリーニングで、ラベルをレース内シャッフルして100回学習し、実importanceが帰無分布の95パーセンタイルを超えない特徴量を候補から落とします。第2段は相関・VIFによる冗長性除去で、ロジット系のみに適用します（GBDTには不要）。第3段は再帰的特徴量削除（RFE）を外側5-foldのCVスコアで評価しながら実行します。

決定的に重要なのは、**この3段すべてを各foldの学習期間内でのみ実行する**ことです。全期間で特徴量を選んでからCVすると選択バイアスが入ります。計算量は跳ね上がりますが、正しさ優先の方針に従います。

### 9.4 キャリブレーション

各モデルの出力に対し、レース内softmax正規化 → 温度スケーリング（単一パラメータ、fold内valid で最適化）→ 必要に応じてベータキャリブレーションを適用します。等張回帰は単調性は保つが確率の総和制約を壊すので、レース内で再正規化を挟みます。評価はReliability Diagram、ECE、そして人気帯別の較正誤差（穴馬の確率が過大評価されていないかは経済性能に直結）で行います。

### 9.5 評価指標

統計指標として、レース内NLL（主指標）、多クラスBrierスコア、Top-1/Top-3精度、NDCG@3、Spearman順位相関、ECEを算出します。

経済指標はトラックBのみで計算可能で、ここが本命です。単勝・複勝・馬連・ワイドについて、期待値閾値を変えたときのROI曲線、的中率、収支の最大ドローダウン、Kelly成長率（1/4 Kelly と 1/10 Kelly）、そして**自己インパクト補正後のROI**を出します。自己インパクト補正は必須で、確定オッズ $o$ に対し投票額 $b$、プール総額 $P$、控除率 $\tau$ のもとで実効オッズを

$$o_{\text{eff}} = \frac{(P + b)(1-\tau)}{S + b}$$

（$S$ は当該組み合わせへの投票額、$S = P(1-\tau)/o$ から逆算）として再計算します。地方の小規模プールではこの補正で期待値が消えるケースが頻出するので、補正前後の両方を報告し、差分を明示します。

有意性は、レースをブロック単位とするブロックブートストラップ（開催日単位、10,000回）で ROI とNLL差の信頼区間を出します。単一の点推定でモデルを選ばないためです。

## 10. 二トラック学習の設計

### 10.1 トラックA（オッズ非使用）

学習対象は2010年以降の全レース、約数百万頭レコードです。市場情報を一切使わないので、モデルは純粋にファンダメンタルズから確率を推定します。運用上の主力であり、また「市場と独立な情報を持っているか」を測る唯一の手段です。

### 10.2 トラックB（オッズ使用）

**この設計の最大の弱点を明示します。** オッズ情報は2026年3月以降しか存在せず、2026年8月時点で約6か月、レース数で7,000〜9,000程度です。これでwalk-forward 5-fold を組むと1 fold が1か月程度になり、統計的検出力が絶望的に不足します。特徴量選択やHPOを回せば確実に過学習します。

現実的な対処として、トラックBを独立モデルとして学習するのではなく、**トラックAの出力を固定オフセットとする残差モデル**として構成します。

$$\text{logit}(\pi_i) = \underbrace{\log p_i^{A}}_{\text{固定オフセット}} + \eta\cdot\text{logit}(q_i^{\text{market}}) + \mathbf{v}_i^\top\alpha$$

ここで $q^{\text{market}}$ は市場暗黙確率、$\mathbf{v}$ はオッズ由来の少数特徴量（オッズ変化率など）です。推定するパラメータを $\eta$ と数個の $\alpha$ に限定すれば、数千レースでも安定します。

この定式化は Bill Benter の市場混合モデル（`docs/Research.md` §2.1）の特殊形で、トラックA側のロジットに掛かる係数を1に固定したオフセットに相当します。将来的にはこの係数（$\alpha_1$）もOOFで自由推定する拡張を検討します。$\alpha_1$ が1から有意に乖離すれば、トラックA自体の較正（§9.4）が本番でズレているシグナルとして使えるためです。ただし数千レース規模での過学習を避けるため、$\alpha_1$ には1付近へ収縮する事前分布（Ridge正則化）を課すことを前提とします（§13.1-4）。

これに加えて、比較のため独立学習版のトラックBも作りますが、その結果は「参考値であり、少なくとも2〜3年のオッズ蓄積まで信頼できない」と明記して扱います。トラックBの本格運用判断は、オッズデータが2年分（2028年春）貯まってからにするのが誠実な判断です。

なお、当日ファイルのオッズスナップショットを今から自前で蓄積すれば（前回のGCP設計の仕組み）、締切直前オッズの時系列という月次ファイルには無い情報が手に入ります。これはローカル開発の段階からでも始める価値があるので、日次取得だけは今日から回しておくことを強く推奨します。過去は取り返せません。

### 10.3 比較の枠組み

最終的に、トラックAの4モデル＋アンサンブル、トラックB（残差版・独立版）の4モデル＋アンサンブル、そしてベースライン3種（市場オッズそのまま、単勝人気順、レース内一様分布）を同一のOOS期間で比較します。**トラックAがオッズベースラインを統計的に有意に上回るかどうか**が、このプロジェクト全体の成否を決める単一の問いです。

## 11. 実行環境と再現性

Pythonは3.12、依存管理は `uv`。主要ライブラリは polars（前処理、pandasより桁違いに速い）、duckdb、lightgbm、torch、numpyro/jax、optuna、scikit-learn、mlflow です。

再現性は乱数シード固定だけでは不十分なので、MLflowで各実行の Gitコミットハッシュ、`conf/` のスナップショット、入力データのmanifest SHA-256集約値、ライブラリバージョン、そして全評価指標を記録します。データセットのバージョンは manifest のハッシュ集約で表現し、`dataset_version` としてタグ付けします。

パイプラインは Prefect または単純な Makefile + CLI で DAG 化し、`nar ingest → nar bronze → nar silver → nar features → nar train --model lgbm --track A → nar evaluate --oos` の順で冪等に実行できるようにします。中間成果物はすべて Parquet でキャッシュし、上流が変わらなければ再計算しません。

テストは、リーク検出のユニットテスト（合成データに未来情報を仕込み、特徴量ビルダーがそれを拾わないことを確認）、as-of 集計の正しさ（手計算した小規模ケースと照合）、スキーマガードの発火、CV分割の重複なし検証を必須とします。**リークテストが最も価値の高いテスト**です。

計算時間の目安は、GPU1枚（RTX 4090級）とCPU16コアで、初回バックフィルとsilver構築が1時間、特徴量構築が2〜3時間、LightGBMのHPO 500試行×5fold が10〜20時間、TabM 300試行が20〜40時間、ベイズのNUTSが数日規模です。ベイズだけは現実的に段階的に進める必要があります。

## 12. 実装順序

最初の週で ingest と manifest を完成させ、全期間のバックフィルを完了させます。次にbronze/silverを作り、**その直後にリーク検証EDA（累積成績8列の時点性）を実施します**。ここでの判定が特徴量設計を左右するので、先に進む前に必ず結論を出してください。

続いて条件付きロジットで最小構成のベースラインを作ります。特徴量10個程度、CV分割だけ正しく実装した状態で、市場オッズベースラインとの比較を出します。この時点でオッズを有意に上回れないなら、モデルの複雑化ではなく特徴量エンジニアリングに戻るべきです。**多くのプロジェクトがここを飛ばして深いモデルに進み、失敗します。**

その後LightGBM、TabM、ベイズを順に追加し、最後にアンサンブルとOOS評価という順序です。

## 13. `docs/Research.md`（外部調査報告書）の反映

`docs/Research.md` は競馬予測の数理モデリングを広く扱った技術調査書ですが、JRA（控除率20〜27.5%）を暗黙の前提にした一般論であり、NARの実データ規模（年間約3万レース）、確定前日データのみという制約、そして本プロジェクトの運用方針（Design_Operation.md、特に「保守的に倒す」「良すぎる結果を疑う」§7.2）とは前提が異なります。以下、採用・保留・不採用を判断根拠つきで整理します。判断基準は (a) NARの実データ規模との整合性、(b) pre-raceスキーマ（§5）との整合性、(c) 運用設計が求める監査可能性・保守性との整合性、の3点です。

### 13.1 即時採用

1. **騎手×調教師の相乗勝率**（Research §3.1）: §6の特徴量カタログに追加済み（`jt_starts_prior` / `jt_winrate_wilson`）。特定厩舎の勝負騎手起用パターンは、騎手単体・調教師単体の収縮勝率では捉えられません。

   **窓の取り方は研究報告書から変更しました。** Research.md は「直近2年」を提案していますが、有界の窓を入れると `conf/features.yaml` の `max_lookback_days` を 730 に上げる必要があり、embargo は そこから自動導出される（CV-04）ため各 fold の学習期間が2年削られます。騎手・調教師の単体特徴量が既に無界（全キャリア）である以上、組み合わせだけ有界にする理由もありません。**窓は無界にし、標本サイズの不確実性は Wilson スコア信頼区間の下限で扱います。** これは「実績の少ないペアを割り引く」という研究報告書の意図をそのまま満たし、embargo を 180 日に据え置けます。

2. **過去走のペースバランス（脚質傾向）**（Research §3.1 Pace Balance）: §6に追加済み（`h_pace_bal_last3`）。当該レースの結果はpost-raceで破棄しますが、馬の過去走の集計値としては使用可能です。

   **定義は取得可能なデータに合わせて変更しました。** Research.md は「前半3F − 後半3F」を提案していますが、NARの月次ファイルに馬ごとのハロンタイムはありません。馬単位で取れるのは `上がり3F` だけなので、前半は差分で作り、距離差を吸収するため 200m あたりに正規化します。

   $$\text{pace\_bal} = \frac{\text{走破タイム} - \text{上がり3F}}{(\text{距離} - 600)/200} - \frac{\text{上がり3F}}{3}$$

   負なら前傾（逃げ・先行型）、正なら後傾（差し・追込型）です。特徴量にするのは直近3走の平均（`h_si_last3` と同じ LAG ベースの決定的な実装）。

   **データ制約**: `上がり3F` は1998〜2009年で56〜94%欠測、2010年以降は約12%欠測です。したがってこの特徴量が実質的に効くのは2010年以降で、それ以前はほぼ全行 NULL になります。学習期間は1998年からなので、前半期はこの特徴量が無い状態で学習することになります。この非対称性はEDAで可視化し、fold ごとの寄与を確認します。
3. **LambdaRankのラベル段階をHPO対象化**（Research §2.2）: §8.2に追記済み。探索空間には入れましたが、**実測では既定の3段階が優りました**（2026-09-03）。

   | 段階数 | レース内 NLL（fold平均） | Top-1 |
   |---|---|---|
   | 3（1着3/2着2/3着1/他0、従来） | **1.78853** | 0.36747 |
   | 5（1着5〜5着1/6着以下0、Research提案） | 1.79052 | 0.36707 |

   差は +0.002 と小さいものの、対象2 fold の両方で符号が一致しています（fold4 +0.00088、fold5 +0.0031）。**既定は3段階に据え置きます。** 想定どおり、NARは少頭数開催が多く、下位グレードを増やすと「実質ほぼ全馬」を区別しようとして信号が薄まります。

   実験条件は `artifacts/label_grade_ab.json`（fold 4-5、固定4年窓）。全fold・拡張窓では10回の学習が現実的な時間で終わらないため範囲を絞っており、**この結果は全期間での厳密な比較ではありません**。ただし差の符号が両foldで一致し、かつ研究報告書の提案が改善する兆候が無い以上、既定を変える根拠はないと判断しました。
4. **Benter型市場混合モデルの係数自由化**（Research §2.1）: §10.2に追記済み。トラックA側ロジット係数を1固定から自由推定へ拡張する余地を残します。

### 13.2 中期採用（Phase 5 候補として実装ロードマップに追加）

1. **Intra-Race Cross-Horse Attention**（Research §2.3-(2)）: 現行のTabM（§8.3）は馬ごと独立入力で、レース内相互作用は集約特徴量（§3.2相当のz-score・softmax・rank ratio）経由でのみ捉えています。NARは出走頭数が少ない開催が多く、Self-Attentionの計算コストが軽いため、TabMのアンサンブル要素として追加する価値はあります。ただし着手はアンサンブル（§8.5）が安定し、OOS評価枠（§9.1）を圧迫しない段階に限ります。
2. **人間関係者の異種グラフ埋め込み**（Research §2.4 HGT/RGCN）: 現行は父・母父の階層ベイズ収縮のみ（§8.4）で、騎手・調教師・馬主・生産者の関係構造は未着手です。ただし順序として、まず13.1-1の相乗勝率特徴量で説明力の天井を確認し、Null Importance（§9.3）で頭打ちが見えてから着手します。GNN埋め込みパイプラインを推論経路に追加する運用コスト（Design_Operation.md）は小さくないため、単純な特徴量で足りるなら追加しません。

### 13.3 保留（時期尚早・データ制約）

1. **Race-Horse Temporal Transformer**（Research §2.3-(1)）: 現行のEMA・ローリング集計（§6）が「休養明けのパフォーマンス変化」「成長曲線」という同じ目的をより軽量に達成しています。NAR年間3万レース規模でTransformerを追加学習させる検証予算はまだなく、TabMベースラインが明確な優位を示すまでは着手しません。
2. **多世代血統グラフ GAT/GraphSAGE**（Research §2.4）: 13.2-2と同じ優先順位の理由に加え、血統データの世代網羅性（母方の世代欠損）自体がEDA（§7）で未検証です。データ品質確認が先です。
3. **複数馬券の同時ポートフォリオ最適化（Multi-Bet Simultaneous Kelly / MIP）**（Research §4.1(2), §4.2）: 設計はDesign_Operation.md §3.5に追加しましたが、運用投入はトラックBの実績が積み上がる段階（Design_Operation.md §9 第4段階以降）に限ります。

### 13.4 不採用

1. **深層強化学習によるベッティング方策**（Research §2.5, PPO/SAC）: Design_Operation.mdの運用方針は「EVとKelly計算過程を人間が追跡・監査できること」「良すぎる結果を自動停止すること」（§7.2）を核に置いています。方策ネットワークが確率推定と資金配分を一体化して直接ベットサイズを出力する設計は、この監査可能性の要求と両立しません。教師あり確率推定とKelly配分の分離を維持します。
2. **量子アニーリングによるQUBO最適化**（Research §6.3）: 本システムの1レースあたり買い目候補数はEVで正の候補に絞り込んだ後で高々数十点です。Research.mdが例示する「3連単4,896通り」規模でも古典MIPソルバ（OR-Tools CP-SAT等）でミリ秒オーダーで解ける問題サイズであり、量子計算を要する規模ではありません。
3. **マルチモーダル基盤モデル**（Research §6.3）: 関係者コメント等のテキストデータを確定前日の範囲でNARから安定取得できるか自体が未検証です。取得経路が確認できるまで棚上げします。

### 13.5 数値目標の扱いについて（注意喚起）

Research.md §5.3 が挙げる目標値（NDCG@1 > 0.82、ROI 108〜115%、Sharpe > 1.8、MDD < 25% 等）は算出条件・出典が明記されておらず、暗黙にJRAを前提にしている可能性が高い値です。NARは控除率・プール規模・出走頭数分布がJRAと異なり、自己インパクト補正（Design_Operation.md §3.3）が必須になるのもこの違いによります。これらの数値をそのまま合否基準として本設計に組み込むことはしません。§9.4・§9.5で定義した自前の評価指標体系とブロックブートストラップ信頼区間を判断基準とし、Research.mdの数値は参考の桁感としてのみ扱います。
