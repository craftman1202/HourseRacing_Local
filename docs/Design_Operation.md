## 1. 運用アーキテクチャの基本方針

### 1.1 責務分離：学習はローカル、推論はクラウド

学習をローカルに置く判断は単なるコスト削減ではありません。設計書のモデル群には NUTS による MCMC が含まれ、これは数日規模の計算になります。この種のワークロードをクラウドで回すと、Vertex AI Training でも Compute Engine の Spot でも月数十ドル以上が確実に発生し、しかも「失敗したら課金だけ残る」性質があります。ローカルの固定資産で回せば追加費用はゼロで、かつ試行回数の制約がなくなります。

一方の推論は、1日あたり最大でも 60〜70 レース、1レース16頭で 1,000 行程度の予測にすぎません。LightGBM と TabM の推論はCPUで数十ミリ秒、ベイズは事後平均を事前計算済みのパラメータテーブルとして持ち出せば単純な行列積です。つまり**推論は Cloud Run のフリー枠に余裕で収まる規模**であり、GPU も常時起動も不要です。

この分離を成立させる鍵が「モデルアーティファクトの契約」です。ローカルとクラウドの間でやり取りするのは、学習済みパラメータと特徴量仕様のみに限定します。

```
gs://nar-model/
  releases/
    v2026.08.24-A/                    # トラックA（オッズ非使用）
      manifest.json                   # 契約の本体
      lgbm_rank.txt                   # LightGBM Booster
      tabm.onnx                       # TabM を ONNX 化（PyTorch 依存を切る）
      clogit_beta.parquet             # 条件付きロジット係数
      bayes_posterior.parquet         # 事後平均・分散のテーブル化
      ensemble_weights.json           # スタッキング重み
      calibration.json                # 温度スケーリング係数
      feature_spec.json               # 特徴量名・順序・dtype・欠損補完規則
      shrinkage_priors.parquet        # 収縮に使う全体平均等の定数
      encoders/                       # カテゴリ→整数の写像（凍結）
    v2026.08.24-B/                    # トラックB（残差モデル）
  current -> releases/v2026.08.24-A/  # ポインタ（GCSオブジェクトとして保持）
```

TabM を ONNX に変換するのは、Cloud Run のコンテナから PyTorch（数百MB）を排除してコールドスタートを短縮するためです。onnxruntime だけなら数十MBで済み、推論レイテンシも改善します。ONNX 変換後は必ず PyTorch 版との出力一致（許容 1e-5）を検証してから公開します。

`manifest.json` には学習に使った `dataset_version`（manifest SHA-256 の集約値）、Git コミットハッシュ、OOS 評価指標、学習期間、そして**特徴量計算に使ったルックバック窓長**を記録します。最後の項目が後述する DB 更新頻度の決定に直結します。

### 1.2 コンポーネント一覧

| 種別 | 名称 | 実装 | 起動契機 |
|---|---|---|---|
| バッチ | `nar-ops`（単一コンテナ・複数エンドポイント） | Python 3.12 / FastAPI | Cloud Scheduler + Cloud Tasks |
| API | `nar-api` | Python 3.12 / FastAPI | HTTP（Web アプリから） |
| フロント | `nar-web` | Next.js 16 (App Router) | Cloud Run（SSR） |

`nar-ops` と `nar-api` を分離するのは、バッチ処理の重い依存（lightgbm, onnxruntime, polars）と API の軽量依存を切り離し、API 側のコールドスタートを 1 秒以下に抑えるためです。Web アプリの体感品質はここで決まります。

## 2. データベース更新戦略（as-of 整合性の保証）

### 2.1 問題の定義

ここが本設計で最も慎重を要する部分です。設計書で定めたとおり、履歴系特徴量は「当該レースの発走時刻より厳密に前」のレコードのみから計算されます。運用時にこれが破れる経路が2つあります。

第一に、**更新遅延によるアンダーカウント**です。前日のレース結果が DB に入っていない状態で当日の推論を行うと、前走情報が欠けた特徴量になります。学習時は完全な履歴から計算されているため、これは学習・推論間の分布不一致（train-serving skew）を生みます。

第二に、**過剰更新によるオーバーカウント**です。同日の先行レースの結果が反映された状態で当日の後続レースを推論すると、それ自体は as-of として正当ですが、**学習時に同じ粒度で計算していなければ不一致になります**。設計書では「同日同場の先行レースは発走時刻順で順序付ける」と定めたので、学習時は日内粒度で as-of 計算されています。したがって運用でも日内粒度を再現する必要があります。

さらに第三の、より厄介な経路があります。NAR の月次ファイルは着順の事後訂正（降着・失格）を反映して書き換わります。すでに特徴量を計算して推論を出した後に過去の結果が変わると、DB の状態と推論時点の DB 状態が乖離し、事後の検証で再現できなくなります。

### 2.2 更新設計

これらを解く方針は「**確定層とライブ層の二層化＋バイテンポラル記録**」です。

確定層（`nar.entry_result_final`）は月次ファイル由来で、日次 02:40 の取り込みで更新されます。ライブ層（`nar.entry_result_live`）は当日ファイル由来で、当日の確定した先行レース結果のみを保持します。特徴量計算は両層の UNION を参照し、`start_ts < 対象レースの発走時刻` で厳密にフィルタします。

```sql
CREATE OR REPLACE VIEW nar.entry_history AS
SELECT race_id, horse_sk, start_ts, finish_pos, speed_index, 'final' AS src
FROM nar.entry_result_final
UNION ALL
SELECT race_id, horse_sk, start_ts, finish_pos, speed_index, 'live' AS src
FROM nar.entry_result_live
WHERE race_id NOT IN (SELECT race_id FROM nar.entry_result_final);
```

更新頻度は次のとおりです。**必要最低限に絞る**という要件に対し、根拠を示します。

| 対象 | 頻度 | 起動 | 根拠 |
|---|---|---|---|
| 確定層（月次ファイル） | 1日1回 02:40 JST | Scheduler #1 | NAR 側の更新が 02:00 頃で、それ以上の頻度は無意味 |
| ライブ層（当日結果） | 1日3回（12:00 / 16:00 / 20:00 JST） | Cloud Tasks | 後述 |
| 特徴量マテビュー | 確定層更新の直後1回のみ | 同一ジョブ内 | 日内変動はライブ層で吸収 |
| 収縮パラメータ・エンコーダ | 更新しない（モデルに凍結） | — | 学習時の値を固定するのが唯一の正解 |

ライブ層を1日3回に留める理由を説明します。当日の先行レース結果が後続レースの特徴量に影響するのは、**同じ馬が同日に複数回出走する場合のみ**です。競走馬は同日に複数レースへ出走しません（ばんえいを除いても平地では制度上ありえない）。したがって「馬の履歴」特徴量に日内更新は不要です。日内更新が意味を持つのは、騎手の当日成績、調教師の当日成績、そして**その日その場の馬場高速度（先行レースのラップから推定する馬場差）**の3系統だけです。

これらは学習時にも日内粒度で計算されているため無視できませんが、更新は「その日の開催が半分進んだ時点」で十分な情報量になります。開催時間帯を3分割する 12:00 / 16:00 / 20:00 の3回が、精度と実行回数のバランス点です。

最後の1系統、馬場差の推定だけは推論の直前に必要なため、これは DB 更新ではなく**推論ジョブ内で当日ファイルから直接計算**します。DB を触らないので更新頻度の問題になりません。

### 2.3 バイテンポラル記録と再現性

推論時点の DB 状態を後から再現できるようにするため、特徴量スナップショットを推論のたびに保存します。

```sql
CREATE TABLE nar.feature_snapshot (
  race_id STRING, horse_no INT64,
  computed_at TIMESTAMP,          -- 特徴量を計算した時刻
  as_of_ts TIMESTAMP,             -- as-of の基準時刻（=発走時刻）
  db_watermark TIMESTAMP,         -- 参照した DB の最終更新時刻
  model_release STRING,
  features JSON,                  -- 全特徴量の値
  feature_spec_hash STRING
) PARTITION BY DATE(as_of_ts) CLUSTER BY race_id;
```

これがあると、後日 NAR 側で着順訂正が入っても「推論時点では何を見ていたか」が完全に残ります。テスト仕様書の RF-04（オッズ・払戻の時点混同）を運用中に検出するための証拠でもあります。ストレージは1日1,000行程度なので BigQuery 無料枠に影響しません。

### 2.4 train-serving skew の常時監視

学習時と推論時の特徴量が同一手続きで計算されていることを、コードの共有だけでなく数値で検証します。

日次 03:30 のジョブで、**前日の全レースについて特徴量を「確定層のみから再計算」し、推論時に保存した `feature_snapshot` と比較**します。一致すべき特徴量（馬の履歴系）が不一致なら即アラートです。不一致が許容されるのは、当日ライブ層に依存する騎手当日成績と馬場差の3系統だけで、それ以外の乖離はバグです。

```python
TOLERATED_DRIFT = {"j_wins_today", "t_wins_today", "track_speed_bias"}
# それ以外の列で相対誤差 > 1e-9 が1件でもあれば Discord に Critical 通知
```

この監視は設計書のリーク対策を運用時にも延長する仕組みで、静かな劣化を防ぐ唯一の手段です。

## 3. 推論パイプライン

### 3.1 タイムライン

Cloud Scheduler は無料枠の3ジョブに厳密に収めます。日内の細かい制御は Cloud Tasks（月100万オペレーション無料）で行います。

| 時刻 (JST) | 処理 | 起動元 | エンドポイント |
|---|---|---|---|
| 02:40 | 月次ファイル取り込み → 確定層 MERGE → 特徴量再構築 | Scheduler #1 | `POST /ingest-and-refresh` |
| 03:30 | skew 検証 → 前日実績の収支確定 → 日次レポート生成 | 同ジョブ内で連続実行 | — |
| 08:00 | 当日スケジュール取得 → Tasks 積み込み | Scheduler #2 | `POST /plan-day` |
| 初回発走 −35分 〜 最終発走 | オッズスナップショット（5分間隔） | Cloud Tasks | `POST /snapshot-odds` |
| 各レース発走 −13分 | 推論実行 → 配信 | Cloud Tasks | `POST /infer` |
| 12:00 / 16:00 / 20:00 | ライブ層更新 | Cloud Tasks | `POST /refresh-live` |
| 月曜 04:00 | モデル鮮度チェック・週次レポート | Scheduler #3 | `POST /weekly-report` |

推論を発走13分前に置く理由は3つの制約の交点です。オッズが実用的な情報量を持つのは締切近くであり早すぎると精度が落ちる、Discord 通知を見てから投票を判断・入力する時間として最低5分は必要、そして推論失敗時に1回リトライしてなお間に合う余裕が要る。13分前なら、推論に30秒、通知に5秒、リトライ1回を含めても発走10分前には手元に届きます。

### 3.2 スケジュール取得と発走時刻変更への追随

`POST /plan-day` は `TodayRaceInfoTop` を1回取得し、開催場・レース番号・発走時刻を抽出して `nar.race_schedule` に UPSERT します。同時に Cloud Tasks へ決定的なタスク名でエンキューします。

```python
task_name = f"infer-{race_id}-{int(start_ts.timestamp())}"
# 同一発走時刻での重複エンキューは Cloud Tasks が ALREADY_EXISTS で自然に弾く
```

発走時刻は実際に変更されます（前レースの裁決長引き、馬場整備、悪天候）。Scheduler を増やさずに追随するため、`POST /snapshot-odds`（5分ごとに走る）の中で毎回スケジュールを再照合します。

```python
def reconcile_schedule(current: dict, stored: dict) -> list[Action]:
    for race_id, new_ts in current.items():
        old_ts = stored.get(race_id)
        if old_ts is None:
            yield Enqueue(race_id, new_ts)                  # 追加開催
        elif abs((new_ts - old_ts).total_seconds()) > 300:   # 5分以上の変更
            yield Delete(f"infer-{race_id}-{ts(old_ts)}")
            yield Enqueue(race_id, new_ts)                   # 新タスク名で再登録
    for race_id in stored.keys() - current.keys():
        yield Delete(...)                                    # 中止・取消
```

閾値を5分にしているのは、1〜2分の微修正で毎回タスクを作り直すと Tasks 操作が無駄に増えるためです。ただし**変更が発走13分前を過ぎてから発生した場合**は再エンキューが間に合わないので、その場合は即時実行に切り替え、通知に「発走時刻変更により推論が遅延」の警告を付けます。

### 3.3 推論処理の内部

`POST /infer` は以下を順に実行します。

まず当日レース情報 ZIP を取得し、対象レースの出馬表を抽出します。ここで `to_prerace()` を通し、着順系・累積成績8列を物理的に落とします。**学習時と完全に同一の関数を共有ライブラリから呼ぶ**ことが絶対条件で、コードの重複実装は禁止します。

レース条件（距離・クラス・賞金）は同じ出馬表ページの `.raceTitle` から読みます。`race_schedule` は `race_id / race_date / baba_code / race_no / start_ts / status` しか持たず、ここを既定値で埋めると**モデルが学習中に一度も見ていない値**が入ります（実際、`class_level` に既定値 1 を渡していた期間があります。学習データの `class_level` は 2 が 77.6%、4 が 19.8%、5 が 2.6% で、1 も 3 も1件も存在しません）。読めなかった場合は固定値に落とさず `InsufficientData` で失敗させます。

学習側の `class_name` は月次ファイルの「競走種類名称」で、普通 / 一般 / 特別 / 重賞 / 準重賞 の5値しか取りません。当日ページの自由文はこの5値へ寄せてから、序数化は学習側の `_class_level` に通します。「特別」は場によって距離表記の前（園田）にも後（船橋）にも出るので、見出し全体を対象にします。

次に BigQuery の `nar.entry_history` から as-of 特徴量を取得します。クエリは `race_date` パーティションを必ず指定し、`require_partition_filter=true` の保護下でスキャン量を抑えます。1レースあたりのスキャンは数十MB以下です。

トラックA と トラックB の両方を計算します。トラックBはオッズが取得できている場合のみ実行し、`feature_spec.json` に定義された市場特徴量が1つでも欠けていればトラックAのみを出力し、その旨をフラグに記録します。ここでオッズ欠損時にゼロ埋めして推論を続けるのは、学習時の分布から外れるので禁止です。

続いて各モデルの予測 → レース内 softmax 正規化 → 温度スケーリング → アンサンブル重み付き幾何平均、の順に処理します。出力確率のレース内総和が 1.0 ± 1e-9 であることをアサートし、破れたら例外を投げて通知を止めます（間違った推論を配信するより、届かないほうがましです）。

期待値計算では、締切前オッズと実測控除率を使い、さらに**自己インパクト補正**を適用します。

$$o_{\text{eff}} = \frac{(P + b)(1-\tau)}{S + b}, \quad S = \frac{P(1-\tau)}{o}$$

プール総額 $P$ は当日ファイルのオッズから逆算できないため、`nar.pool_size_model`（過去実績から場×クラス×曜日で推定した中央値テーブル）を使います。この推定は保守的に（小さめに）見積もり、期待値を過大評価しない側に倒します。

推奨投資額は 1/4 Kelly で算出し、設定上限（`MAX_BET_PER_RACE`、`MAX_BET_PER_DAY`）でクリップします。上限は環境変数で管理し、コードに埋め込みません。

結果を `nar.prediction` と `nar.bet_candidate` に書き、`nar.feature_snapshot` に特徴量を保存し、Discord へ配信します。

### 3.4 冪等性と失敗時の挙動

すべての書き込みは `(race_id, model_release, computed_at)` を主キーとする MERGE で、同一タスクの再実行が重複を生みません。Discord 通知だけは冪等にできないため、`nar.notification_log` に `(race_id, channel, dedupe_key)` を記録し、既送信なら送信をスキップします。

失敗時の分岐は明示的に設計します。NAR からのデータ取得失敗はリトライ対象（Cloud Tasks が最大3回、間隔 30s / 90s / 270s）。BigQuery 一時エラーもリトライ対象。**特徴量の欠損やアサーション違反はリトライしない**（同じ結果になるため）でエラー通知のみ。発走時刻を過ぎたタスクは実行せず破棄します。遅れた推論を配信するのは害しかありません。

## 4. Discord 配信

### 4.1 設定

`.env`（Secret Manager 経由で Cloud Run に注入）で管理します。

```env
DISCORD_WEBHOOK_PREDICTION=https://discord.com/api/webhooks/xxx/yyy
DISCORD_WEBHOOK_ALERT=https://discord.com/api/webhooks/aaa/bbb
DISCORD_WEBHOOK_DAILY=https://discord.com/api/webhooks/ccc/ddd
DISCORD_MIN_EV=1.05          # この期待値未満は通知しない
DISCORD_RATE_LIMIT_RPS=0.4   # 30 req/min 制限に対する安全マージン
```

チャンネルを3系統に分けるのは、レース直前の通知に埋もれてアラートを見落とすのを防ぐためです。Secret Manager はシークレット1つあたり月6アクセス以内なら無料枠に収まり、起動時に1回読むだけなので実質無料です。

### 4.2 Discord API の制約と実装

Discord Webhook には厳格な制限があります。1メッセージあたり embed は最大10個、**全 embed の文字数合計が 6,000 文字**、embed の description が 4,096 文字、field が 25 個まで、そして Webhook あたり**毎分30リクエスト**のレート制限です。

地方競馬は1日60レース以上あり、発走時刻が重なる場（3場同時開催）では短時間に複数の通知が集中します。素朴に実装すると 429 を踏みます。対策として、送信は必ずレート制限付きキューを通し、429 応答時は `Retry-After` ヘッダを尊重して待機します。加えて、同時刻帯（±3分）に複数レースの推論が完了した場合は、1メッセージに複数 embed をまとめて送ります。

```python
async def send(webhook: str, embeds: list[Embed]) -> None:
    for chunk in batch(embeds, max_count=10, max_chars=5500):  # 6000に余裕
        async with rate_limiter:
            r = await client.post(webhook, json={"embeds": [e.dict() for e in chunk]})
            if r.status_code == 429:
                await asyncio.sleep(float(r.headers.get("Retry-After", 5)) + 0.5)
                continue  # 同一チャンクを再送
            r.raise_for_status()
```

文字数上限は 5,500 で切ります。マルチバイト文字の数え方で境界事故が起きやすいので、余裕を持たせるのが安全です。

```
│  11  キタノコマンド     14.2%  8.3% 1.41  単勝 ¥900
│
│  買い目合計 ¥2,100 (1/4 Kelly, 本日残枠 ¥7,900)
│  自己インパクト補正後 EV: 7番 1.24 / 11番 1.33
│  ⚠ 想定プール ¥1.4M（推定値・実測より小さめに見積り）
└─ [Web で詳細を見る]
```

EV が閾値未満のレースは「推奨なし」として通知自体を省略します。1日60レースすべてを通知すると通知疲れで見なくなり、それが最大の運用リスクです。ただし省略したレースも Web アプリでは全件閲覧できます。

Discord の embed color をトラックA/B と EV 水準で変え、視認性を上げます（EV ≥ 1.2 は緑、1.05〜1.2 は黄、参考表示は灰）。

日次サマリは 03:30 のジョブから送ります。前日の的中率、収支、モデル NLL、skew 検証結果、そして**「推奨したが投票しなかった分」の仮想収支**を含めます。後者は運用規律の自己評価に効きます。

アラート通知は、データ取得失敗、スキーマドリフト検出、skew 検証の不一致、テスト仕様書 RF系ガードの発火、そして日次予算超過の5種類です。

## 5. Web アプリケーション

### 5.1 技術選定

サブスクリプション品質を目標とするため、選定は「体感速度」「型安全」「運用コストゼロ」の3軸で行います。

フレームワークは **Next.js 16 (App Router)** を採用します。TanStack Start も有力な選択肢で、Vite ベースの開発体験と型安全なルーティングは魅力的ですが、2026年時点でエコシステムの成熟度と採用時の情報量では Next.js が優位です。個人開発で長期メンテする前提では、詰まったときに答えが見つかるかどうかが実質的な生産性を決めます。React Server Components で BigQuery からのデータ取得をサーバ側に閉じ込め、クライアントへは整形済みの最小データだけを送ります。

| レイヤ | 技術 | 選定理由 |
|---|---|---|
| フレームワーク | Next.js 16 App Router / React 19 | RSC でクライアントバンドルを最小化、Partial Prerendering で初期表示が速い |
| 言語 | TypeScript strict | API 境界の型を後述の方法で自動同期 |
| スタイル | Tailwind CSS v4 + shadcn/ui | 手早く一貫したデザイン、CSS-in-JS のランタイムコストなし |
| データ取得 | TanStack Query v5（クライアント側の更新系のみ） | オッズのポーリング更新に最適、キャッシュ制御が明快 |
| チャート | Visx（または Recharts） | OOS 較正曲線や資金曲線のような非定型グラフに強い |
| テーブル | TanStack Table v8 | 仮想スクロールで数万行のレース履歴を扱う |
| 認証 | Auth.js v5（Google OAuth）+ 単一テナントの許可リスト | 自分専用なら最小構成、サブスク化時に Stripe を足せる |
| API | FastAPI + Pydantic v2 → OpenAPI → `openapi-typescript` で型生成 | Python の推論ロジックを再実装せずに済む |
| リアルタイム | SSE（Server-Sent Events） | WebSocket は Cloud Run と相性が悪く、単方向配信なら SSE で十分かつ安価 |
| 監視 | Sentry 無料枠 | フロント・バックのエラーを一元化 |

API を Python の FastAPI にするのは重要な判断です。期待値計算、Kelly 算出、自己インパクト補正といったロジックは推論パイプラインと**完全に同一の実装を共有しなければなりません**。TypeScript で再実装すると必ず乖離し、Web に表示される数値と Discord に届く数値が違う、という最悪のバグを生みます。OpenAPI スキーマから TypeScript 型を自動生成すれば、型安全性は保ったまま単一実装を維持できます。

リアルタイム更新に SSE を選んだのは、Cloud Run の課金モデルとの相性です。WebSocket は接続維持中ずっとインスタンスが生き、リクエストベース課金の恩恵を失います。SSE でも接続は維持されますが、オッズ更新の5分間隔に合わせて「30秒接続して切る」ポーリング的な使い方にすれば課金を最小化できます。実際には TanStack Query の `refetchInterval` による通常ポーリングで十分で、SSE はレース直前の10分間だけ有効にする設計にします。

### 5.2 画面設計

**（1）ダッシュボード `/`**

本日の全開催を1画面に集約します。上部に場別のタイムライン（横軸が時刻、各レースがブロック、EV 閾値超えは色付き）を置き、次の推奨レースまでのカウントダウンを大きく表示します。ここが最も見られる画面なので、Partial Prerendering で静的部分を即座に返し、動的部分だけをストリーミングします。

サイドに本日の投資枠の消化状況（Kelly 上限に対する残枠）、直近30日の資金曲線のスパークライン、システムヘルス（最終 DB 更新時刻、モデルリリース、skew 検証の合否）を配置します。

**（2）レース詳細 `/race/[raceId]`**

出馬表を予測確率の降順で表示し、各馬について予測確率、市場暗黙確率、EV、自己インパクト補正後 EV、推奨投資額を並べます。予測確率と市場確率の乖離を横棒で可視化すると、どこにエッジがあるかが一目で分かります。

4モデル（条件付きロジット、LightGBM、TabM、ベイズ）それぞれの予測を展開表示でき、モデル間の不一致が大きいレースは「意見が割れている」と明示します。アンサンブルの合意度は実質的な信頼度指標なので、これを表に出すのは価値があります。ベイズモデルからは予測確率の信用区間も出せるので、それをエラーバーで重ねます。

オッズの時系列チャート（発走前30分間の推移）と、モデル確率との乖離の推移も置きます。締切直前にオッズが動いてエッジが消えるパターンを目で確認できるようにします。

**（3）OOS パフォーマンス `/performance/oos`**

テスト仕様書で定義した指標をそのまま可視化します。レース内 NLL・Top-1精度・Top-3精度・Brier・ECE を、モデル別・トラック別に市場ベースラインと並べて表示します。較正曲線（Reliability Diagram）は10分位ビンで、人気帯別（1〜3人気／4〜7／8人気以下）に分けて3枚並べます。全体で良好でも穴馬帯だけ崩れているパターンが見えるようにするためです。

EV 閾値を変えたときの ROI 曲線を、自己インパクト補正の前後で2本重ねて描きます。この2本の差が「机上の期待値と現実の差」であり、最も直視すべき情報です。ブロックブートストラップ95%信頼区間を帯で表示し、点推定だけを見ないようにします。

**（4）運用実績 `/performance/live`**

推奨と実投票を分けて集計します。「モデルが推奨した全ベットを機械的に実行した場合」の仮想収支と、「実際に投票した分」の実収支を並べ、乖離の理由（見落とし、判断で見送り、資金制約）を記録できるようにします。この乖離の管理が長期運用の実質的な成否を決めます。

累積収支曲線、月別 ROI、券種別成績、場別成績、そして**予測確率の実測較正**（本番データでの Reliability Diagram）を表示します。最後の項目は OOS 評価との比較で、モデルの劣化を最も早く検知できる指標です。加えて最大ドローダウンと現在のドローダウン深度を常時表示し、事前に決めた撤退基準に対する現在位置を明示します。

**（5）モデル管理 `/models`**

`gs://nar-model/releases/` の一覧を表示し、各リリースの `manifest.json`（学習期間、dataset_version、Git コミット、OOS 指標）を並べます。`current` ポインタの切り替えをここから行えるようにしますが、切り替えには OOS 指標が現行を上回っていることのチェックを必須にします。承認なしでの本番切り替えは事故の温床です。

### 5.3 デザイン品質

サブスク品質を名乗るなら、以下は妥協できません。ダークモード優先（ナイター開催を見ながら使うため）、レース直前の残り時間表示は 1 秒更新でクライアント側計算（サーバ負荷ゼロ）、モバイル最適化（実際の投票はスマホで行うため、推奨買い目を**タップでクリップボードにコピー**して各投票サイトに貼れる導線が必須）、数値のスケルトンローディングとオプティミスティック更新、そして Lighthouse の Performance / Accessibility が 90 以上。

投票サイトの一括投票フォーマットに合わせたテキスト生成（楽天競馬形式・SPAT4形式を切替）をコピーボタンで提供するのが、実運用で最も効く機能です。ここが手作業だと入力ミスで損失が出ます。

### 5.4 デプロイと配信

Cloud Run に `nar-web` と `nar-api` を配置し、いずれも `min-instances=0`、`concurrency=80`、**リクエストベース課金**に設定します。リクエストベース課金はアイドル時の CPU 課金が発生しないため、アクセスが散発的な個人利用では大幅に安くなります。

静的アセットは Cloud Run から配信すると egress 課金が乗るので、Firebase Hosting（無料枠 10GB/月転送）を前段に置き、`/api/*` と SSR パスだけ Cloud Run に rewrite します。この構成なら実質的な転送費用がゼロになります。

コールドスタートは Next.js の standalone 出力と、API 側の軽量依存で 1〜2 秒に収まります。個人利用ならこれで十分ですが、サブスク提供するなら日中だけ `min-instances=1` にする Cloud Scheduler での動的切り替え（`gcloud run services update`）が現実的な妥協点です。ただしこれは月額で数ドルの追加になるので、収益が出るまでは 0 のままにします。

## 6. コスト設計

### 6.1 見積もり

> 実測による改訂（2026-08-28）: `nar-ops` は **2vCPU・4GiB** が必要。
> 1GiB では推論中に上限超過（実測 1041 MiB）でインスタンスが落ち、
> 応答は 503 になる。条件付きロジット・LightGBM・TabM(ONNX) を同時に
> 載せ、そこへ BigQuery の履歴取得結果が乗るため。
> 起動回数は当初見積もりの 500/日 に対し実測 65/日（推論 20 + オッズ 45）
> なので、単価が上がっても無料枠には収まる
> （vCPU 秒 12万 / 24万、GiB 秒 24万 / 45万）。


| 項目 | 使用量 | 無料枠 | 月額 |
|---|---|---|---|
| Cloud Run `nar-ops` | 約 65 起動/日、2vCPU・4GiB、推論 60 秒・その他 15 秒 | 240k vCPU秒 / 450k GiB秒 | $0 |
| Cloud Run `nar-api` | 約 3,000 req/月、0.5vCPU・512MiB、平均 0.3 秒 | 同上（合算） | $0 |
| Cloud Run `nar-web` | 約 2,000 req/月、1vCPU・512MiB | 同上（合算） | $0 |
| Cloud Scheduler | 3 ジョブ | 3 ジョブ | $0 |
| Cloud Tasks | 約 9,000 op/月 | 1,000,000 | $0 |
| BigQuery ストレージ | 6〜9 GB（アクティブ） | 10 GiB | $0 |
| BigQuery クエリ | 30〜80 GB/月 | 1 TiB | $0 |
| GCS `nar-raw` | 20〜35 GB（ライフサイクル適用後） | — | $0.4〜0.8 |
| GCS `nar-model` | 1〜3 GB（リリース10世代保持） | — | $0.02〜0.06 |
| Secret Manager | 3 シークレット、月 100 アクセス | 6 シークレット / 10k アクセス | $0 |
| Artifact Registry | イメージ 3 種 × 400MB | 0.5 GB | $0.1〜0.2 |
| Firebase Hosting | 転送 1〜2 GB/月 | 10 GB | $0 |
| **合計** | | | **$0.5〜1.1** |

Cloud Run の合算使用量を計算すると、`nar-ops` が 500 × 20 × 1 = 10,000 vCPU秒/日 = 300,000 vCPU秒/月 となり、これは無料枠 240,000 を超えます。超過分 60,000 秒 × $0.000024 = 約 $1.4 が発生します。

これを削るには2つの手があります。ひとつは `nar-ops` のメモリを 512MiB に落とし処理時間を詰めること。もうひとつは、`snapshot-odds` の頻度をレース直前帯（発走15分前〜発走）に限定し、それ以外を10分間隔にすることです。後者を採用すると起動回数が約 300/日 に減り、180,000 vCPU秒/月で無料枠内に収まります。オッズの情報価値は締切直前に集中しているので、精度への影響はほぼありません。**この調整を採用**し、合計を $1 以下に維持します。

Artifact Registry は 3 イメージ × 複数世代で無料枠 0.5GB を超えやすいため、`keep-last-3` のクリーンアップポリシーを設定します。マルチステージビルドとベースイメージの共有（`python:3.12-slim` を全イメージで統一）でレイヤキャッシュを効かせれば、実効サイズは大幅に減ります。

### 6.2 コスト事故の予防

課金が跳ねる典型パターンを列挙し、それぞれに機械的な防御を置きます。`min-instances > 0` の設定はコードレビューで禁止し、Terraform に `min_instance_count = 0` をハードコードします。BigQuery のパーティションフィルタ必須（`require_partition_filter = true`）を全テーブルに設定し、フルスキャン事故を物理的に防ぎます。GCS のライフサイクル（30日 Nearline、365日 Coldline、日次オッズ生データは1,095日で削除）を Terraform で管理します。予算アラートを $3 と $5 の二段で設定し、$5 到達時は Pub/Sub 経由で Cloud Run サービスを自動停止するトリガーを置きます。最後に、Vertex AI と Cloud SQL を組織ポリシーで無効化します。この2つが最も高額な誤用先です。

BigQuery の代替として Neon や Supabase の無料枠も検討しましたが、Neon の無料枠はストレージ 0.5GB / プロジェクトと compute-hours 制限があり、数百万行の履歴と as-of ウィンドウ集計には不足します。BigQuery 無料枠（ストレージ 10GiB、クエリ 1TiB/月）のほうが本ワークロードには明確に適合します。

## 7. 監視・アラート・SLO

### 7.1 SLO

個人運用でも SLO を決めておくと、どこまで作り込むかの判断が明確になります。

| 指標 | 目標 | 測定 |
|---|---|---|
| 推論配信の適時性 | 対象レースの 95% で発走10分前までに Discord 到達 | `notification_log.sent_at` と `start_ts` の差 |
| 推論のカバレッジ | 開催レースの 98% 以上で推論成功 | `prediction` 行数 / `race_schedule` 行数 |
| DB 鮮度 | 確定層が毎日 04:00 までに前日分を反映 | `db_watermark` の監視 |
| skew 検証 | 許容外の特徴量乖離が 0 件 | 3.4 節の日次検証 |
| Web 可用性 | 月間 99% | Cloud Monitoring の uptime check（無料枠内） |

### 7.2 アラート

Discord のアラートチャンネルへ送る条件を明示します。データ取得の連続失敗（3回以上）、スキーマドリフト検出、skew 検証の不一致、推論カバレッジが 90% 未満、モデルの鮮度超過（`current` の学習日が90日以上前）、予算アラート、そして**テスト仕様書 RF系ガードの本番発火**です。

最後の項目を運用に組み込むのが重要です。本番の直近30日の実測 Top-1 精度が 60% を超えた、あるいは補正前 ROI が 130% を3か月継続した場合、それは成功ではなくパイプラインの破損を示唆します。この検出を月曜の週次ジョブで自動実行し、発火したら**推奨の配信を自動停止**します。良すぎる結果を信じて資金を投じるのが、この種のシステムで最も高額な失敗です。

### 7.3 モデル劣化の検知

本番データでの較正誤差（ECE）を30日移動窓で計算し、OOS 評価時の値から 0.02 以上悪化したらアラートします。加えて特徴量分布の PSI を月次で計算し、0.25 を超えた特徴量があれば分布シフトとして報告します。地方競馬では開催場の改修（コース形態の変更）や制度変更が実際に起こるので、この監視は必須です。

劣化を検知したら、ローカルで再学習して新リリースを作り、OOS を新しい期間に更新して評価し、指標が上回った場合のみ `current` を切り替えます。再学習の頻度は四半期ごとを基本とし、劣化検知時は随時とします。

## 8. リリース運用

### 8.1 モデルのプロモーション手順

ローカルで学習が完了したら、`nar model publish` コマンドで以下を自動実行します。ONNX 変換と PyTorch 版との出力一致検証、`feature_spec.json` の生成、GCS へのアップロード、そして**シャドー推論**の起動です。

シャドー推論は、新リリースを `current` にせず、既存の推論ジョブ内で並列に実行して `nar.prediction_shadow` に書くだけの運用です。2週間シャドーを回し、本番モデルとの予測乖離、実測較正、レイテンシを比較したうえで切り替えます。切り替えは GCS の `current` ポインタ更新のみなので、ロールバックは即座に可能です。

### 8.2 インフラの管理

Terraform で全リソースを管理し、`terraform plan` の差分をレビューしてから適用します。CI（GitHub Actions の無料枠）では、テスト仕様書のユニット・結合テストを実行し、パスしたらイメージをビルドして Artifact Registry に push、Cloud Run へデプロイします。リーク検証テスト（LK系）は nightly で走らせ、失敗したらデプロイを停止します。

サービスアカウントは最小権限で、`nar-ops` は GCS オブジェクト作成、BigQuery データ編集、Cloud Tasks エンキュー、Secret Manager 読み取りのみ。`nar-api` は BigQuery 読み取りのみ。`nar-web` は API 呼び出しのみです。Scheduler と Tasks からの呼び出しは OIDC 認証で、Cloud Run は `--no-allow-unauthenticated` にします。

### 8.3 ランブック

日常の異常に対する対処手順を用意しておきます。

NAR サイトがダウンしている場合は、当日の推論を全面スキップし Discord に告知します。部分的に取得できる場合も、`to_prerace` を通せない不完全データでの推論は禁止です。スキーマドリフトが出た場合は、確定層への MERGE を停止したまま原本 ZIP を保全し、ローカルでパーサを修正して再デプロイします。**原本があるので過去データの再取得は不要**で、これが2章の設計が効く場面です。

BigQuery のクエリコストが無料枠に迫った場合は、`feature_snapshot` の JSON 列を圧縮するか、直近90日以外をパーティション削除します。推論に必要なのは直近の履歴と特徴量スペックだけで、監査目的の古いスナップショットは GCS にエクスポートして退避できます。

skew 検証が不一致を出した場合は、**その日の推奨配信を停止**し、原因を特定するまで再開しません。乖離した特徴量名がログに出るので、`nar diff-features --race-id ...` で該当レースの学習時計算と推論時計算を並べて比較します。

## 9. 運用開始までの段階計画

第1段階（2週間）は配信なしのシャドー運用です。パイプラインを全部動かし、`nar.prediction` にデータを溜めるだけで、Discord への推奨配信もWebの推奨表示もオフにします。ここで検証するのは適時性・カバレッジ・skew の3点で、システムの正しさだけを確認します。

第2段階（1〜2か月）はペーパートレード配信です。Discord に推奨を流し、Web で実績を追いますが、実際の投票は行いません。仮想収支と OOS 評価の整合を確認します。ここで自己インパクト補正後の ROI が 100% を安定して超えないなら、次段階には進まないという判断基準を事前に決めておきます。

第3段階が最小額での実運用です。1レースあたりの上限を数百円に設定し、Kelly 比率を 1/10 に落とします。実際に投票してみると、締切に間に合わない、オッズが動いてエッジが消える、入力ミスをする、といった机上では見えない摩擦が必ず出ます。それを洗い出す段階です。

第4段階で初めて 1/4 Kelly と本来の上限に上げますが、この判断は第3段階で3か月以上の実績が出てからにしてください。

## 10. 最後に

この設計はコスト・再現性・as-of 整合性の3点を優先して組んであり、月額 $1 前後で完全自動運用できます。技術的には堅牢に作れますが、控除率 20〜25% という市場構造は設計では変えられません。7.2 節の「良すぎる結果の自動停止」と 9 章の段階計画は、システムの品質保証というより、**自分自身の判断を守るための仕組み**として置いています。
