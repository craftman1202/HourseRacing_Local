# 地方競馬予測システム オペレーション設計 検証テスト仕様書 v1.0

## 0. 本書の位置づけ

本書は「オペレーション設計書」に記載された運用系実装（モデル配布、DB 更新戦略、推論パイプライン、Discord 配信、Web アプリ、コスト・監視・リリース運用）が設計意図どおりに動作することを機械的に判定するためのテスト仕様である。学習パイプライン側（取得・リーク・CV・モデル品質）は既存の「実装検証テスト仕様書（IG/LK/CV/FE/MD/RF 系）」が担当し、本書はその成果物を**運用境界で正しく再現できているか**に焦点を絞る。両者は重複させず、接続点のみ本書の SK 系（skew）と RL 系（リリースゲート）で参照する。

対象外は、賭式そのものの収益性検証（EV 系は学習側仕様書の EV/RF 系）と、法務レビュー・資金管理方針の妥当性（テストで担保できない領域として §12 のリスク登録に記載）。

## 1. テスト戦略

### 1.1 テストレベル

運用系は外部依存（NAR サイト、GCP マネージドサービス、Discord）が多く、すべてを実物で検証するとコストと不確実性が跳ね上がる。したがって「同じ不変条件を、レベルを変えて二度検証する」方針を取る。ロジックは L0/L1 で網羅し、配線（IAM・環境変数・スケジュール・型）は L2/L3 で最小回数だけ検証する。

| レベル | 名称 | 外部依存の扱い | 実行頻度 | 所要目標 |
|---|---|---|---|---|
| L0 | ユニット | 全モック、純関数 | 全 push | 60 秒以内 |
| L1 | コンポーネント | HTTP/GCS/BQ を代替実装（後述） | 全 push | 5 分以内 |
| L2 | 統合 | エミュレータ＋一時 BQ データセット | PR マージ時、日次 | 20 分以内 |
| L3 | E2E（ステージング） | 実 GCP・実 Discord（テスト用 webhook）・NAR は録画応答 | リリース前、週次 | 60 分以内 |
| L4 | 本番合成監視 | 実本番、合成レース ID | 常時（15 分毎） | ― |

### 1.2 判定区分と重大度

判定区分は、**不変条件**（データや環境に依存せず必ず成立すべき論理・数式。失敗＝バグ確定）、**閾値条件**（データ依存で許容範囲を持つ。失敗＝調査必須）、**SLO**（運用実績の統計値。ウィンドウ内での違反率で判定）の 3 種。重大度は Blocker（デプロイ・本番投入を停止）、Critical（当該機能を無効化して継続、24 時間以内修正）、Warning（記録とダッシュボード表示のみ）とする。

Blocker に指定するのは「静かに間違った金額を賭ける」経路に直結する項目に限定する。具体的には SK-01/02（skew ゼロ）、DB-03（as-of 汚染）、IN-05（オッズ欠損時のゼロ埋め禁止）、IN-08（冪等性）、CO-01（課金ガード）、RL-04（モデルハッシュ検証）である。

### 1.3 pytest 実装方針

マーカーは `unit` / `component` / `integration` / `e2e` / `synthetic_monitor` / `slow` / `costly` を用い、CI ジョブはマーカー選択のみで切り替える。`costly` は実 GCP 課金または実 Discord 送信を伴うものとして明示的にオプトインさせる。

時刻依存ロジックは全て注入された `Clock` プロトコル経由とし、テストでは固定クロックを使う（`freezegun` はライブラリ内部の時刻取得を漏らすため、境界テストの主軸には使わない）。乱数・ハッシュシードは fixture で固定し、同一入力に対する出力の SHA-256 一致を決定論テストの共通判定手段とする。

外部依存の代替実装は次の対応とし、L1 と L2 で同一テスト関数をパラメトライズして流用する（`pytest` の間接パラメトライズで backend を切替）。

| 依存 | L1 代替 | L2 実体 | 検証したい差分 |
|---|---|---|---|
| NAR HTTP | 録画レスポンス（ZIP/HTML のゴールデン）を返すローカルサーバ | 同左（本番サイトへは打たない） | 文字コード・スキーマ差分 |
| GCS | インメモリ／ローカル FS 実装 | fake-gcs-server コンテナ | 条件付き書き込み・世代番号 |
| BigQuery | SQL を DuckDB 方言変換して実行 | 一時データセット（テスト後削除） | MERGE 意味論・パーティション |
| Cloud Tasks | インプロセスキュー（タスク名一意制約を再現） | 実キュー（ステージング） | 重複 enqueue・リトライ |
| Discord | ローカル受信サーバ（レスポンスコード注入可） | テスト用 webhook | レート制限・埋め込み上限 |
| Scheduler | cron 式パーサでの静的検証 | Terraform plan 検証 | ジョブ数・タイムゾーン |

### 1.4 テストデータ

固定フィクスチャは 3 系統を用意する。第一に**ゴールデン開催日**（実データ由来。複数場同時開催、10 レース以上、確定オッズ有り）。第二に**合成異常日**（出走取消・競走除外・同着・発走時刻変更・開催中止・1 頭立て・レース番号欠番を人工的に含む）。第三に**時系列フィクスチャ**（アラート条件と SLO 判定用の、ECE/PSI/カバレッジの合成時系列）。いずれもリポジトリ内でハッシュ固定し、変更時は差分レビューを必須とする。

## 2. モデル配布・アーティファクト（MP）

ローカル学習と GCP 推論を分離した設計の弱点は「配布物の取り違え」である。したがって manifest を単一の真実とし、実行時に自己検証させる。

| ID | 検証内容 | 期待値 | 区分 | 重大度 | L |
|---|---|---|---|---|---|
| MP-01 | manifest 必須フィールド | `model_id, dataset_version, train_period, feature_spec_hash, model_sha256, oos_metrics, lookback_days, track(A/B), calibration` が全て存在し型検証を通る | 不変 | Critical | L0 |
| MP-02 | アーティファクト完全性 | 起動時に実ファイルの SHA-256 が `model_sha256` と一致。不一致で起動失敗（ヘルスチェック赤） | 不変 | Blocker | L1 |
| MP-03 | feature_spec 整合 | 推論コードが生成する特徴量名・順序・dtype のハッシュが `feature_spec_hash` と完全一致 | 不変 | Blocker | L1 |
| MP-04 | lookback 整合 | manifest の `lookback_days` が as-of 集計の最長ウィンドウ以上。未満なら起動失敗 | 不変 | Critical | L0 |
| MP-05 | current ポインタ | `current` は releases 配下の実在ディレクトリを指し、切替は原子的（読み取り中の推論は旧版で完走） | 不変 | Critical | L2 |
| MP-06 | バージョン混在禁止 | 1 推論内で参照される全モデルの `dataset_version` が一致。異なる場合は例外 | 不変 | Critical | L1 |
| MP-07 | ONNX 等価性 | 元モデルと変換後の予測差が全サンプルで最大絶対差 < 1e-5、Top-1 一致率 100% | 閾値 | Blocker | L1 |
| MP-08 | ロールバック | 直前リリースへの切替が 5 分以内に完了し、切替後の推論が旧版 manifest を報告 | 閾値 | Critical | L3 |

## 3. DB 更新戦略（DB）

確定層／ライブ層の二層構造と「必要最低限の更新頻度」が、as-of 集計の正しさを崩さないことを検証する。

| ID | 検証内容 | 期待値 | 区分 | 重大度 | L |
|---|---|---|---|---|---|
| DB-01 | 確定層 MERGE 冪等 | 同一月次データを 2 回 MERGE 後、行数・全列ハッシュが 1 回目と完全一致 | 不変 | Blocker | L1/L2 |
| DB-02 | 二層の重複排除 | `entry_history` ビューで同一 `(race_id, horse_sk)` が 2 行以上になるケースが 0 件（ライブ→確定の吸収境界を含む） | 不変 | Blocker | L1 |
| DB-03 | as-of 汚染 | 対象レース発走後の実績行を注入しても、当該レースの全特徴量がビット単位で不変 | 不変 | Blocker | L1 |
| DB-04 | 鮮度ゲート（fail-closed） | 確定層の最新確定日が「前日」未満なら推論を実行せずアラートのみ。ベット候補 0 件 | 不変 | Blocker | L1 |
| DB-05 | 日内更新の対象限定 | 12/16/20 時の更新で変化する系統が騎手・調教師・馬場差の 3 系統のみ。他系統の差分行 0 件 | 不変 | Critical | L1 |
| DB-06 | 更新頻度の遵守 | 24 時間で確定層マージ 1 回、ライブ更新 3 回。超過実行は前回実行記録により no-op | 閾値 | Warning | L2 |
| DB-07 | 後日訂正の反映 | 過去月 ZIP のハッシュ変化を検知すると `is_final` を解除、再取得後 MERGE で上書きし、旧値が監査テーブルに残る | 不変 | Critical | L1 |
| DB-08 | 訂正後の再評価 | 訂正が影響した日の `pnl_daily` が再計算され、Web/OOS 表示値が更新される | 不変 | Critical | L2 |
| DB-09 | パーティション制約 | 全クエリが `require_partition_filter` を満たし、フルスキャンが発生しない（走査バイト数が閾値以下） | 閾値 | Critical | L2 |
| DB-10 | タイムゾーン | 保存は UTC、境界判定は JST。日付境界（00:00 JST 前後）のレースが正しい営業日に属する | 不変 | Critical | L0 |

## 4. 学習／推論 skew（SK）

本設計の最大の失敗モードは「学習時と違う条件のデータで推論する」ことである。ここは許容差ゼロで運用する。

| ID | 検証内容 | 期待値 | 区分 | 重大度 | L |
|---|---|---|---|---|---|
| SK-01 | 特徴量再現 | 前日分の `feature_snapshot` と、確定層のみから再計算した値の不一致 0 件（数値は相対誤差 1e-9 以内） | 不変 | Blocker | L2 |
| SK-02 | コード経路同一 | 学習時と推論時が同一モジュール・同一関数を呼ぶ（呼び出しグラフの検証、重複実装の存在で失敗） | 不変 | Blocker | L0 |
| SK-03 | ホワイトリスト差分 | 日内更新に起因する差分は定義済みホワイトリスト列のみ。列外の差分は即 Blocker | 不変 | Blocker | L2 |
| SK-04 | 欠損表現 | 欠損の内部表現（NaN／未出走フラグ）が学習時と一致。ゼロ・平均代入が発生しない | 不変 | Blocker | L0 |
| SK-05 | カテゴリ未知値 | 学習時に存在しないカテゴリ（新規騎手など）が既定の未知カテゴリへ写像され、例外にならず予測が生成される | 不変 | Critical | L1 |
| SK-06 | snapshot 保全 | 推論に使った特徴量が必ず保存され、後から DB 状態を再現できる（保存漏れ 0 件） | 不変 | Critical | L1 |
| SK-07 | skew 検証ジョブ | 03:30 ジョブが不一致検出時に Discord アラートを送出し、当日の推論を縮退モードへ切替 | 不変 | Critical | L2 |

## 9. コスト・監視（CO / MO）

コストは「実測してから気付く」では手遅れになるため、IaC の静的検査と見積シミュレーションをテストとして固定化する。

| ID | 検証内容 | 期待値 | 区分 | 重大度 | L |
|---|---|---|---|---|---|

## 11. 受け入れ判定（Definition of Done）

段階的導入の各ゲートで必要なテスト ID を固定する。ゲート通過は「該当 ID が全 GREEN」かつ「Blocker 未発火」を条件とする。

| ゲート | 対象 | 必須 GREEN |
|---|---|---|
| G1 シャドー運用開始 | データ蓄積のみ | MP-01〜07、DB-01〜10、SK-01〜07、SC-01〜05、DR-01〜06、CO-01〜05、RL-02/04/06 |
| G2 ペーパートレード | Discord・Web 公開 | G1 ＋ IN-01〜12、DC-01〜10、WB-01〜09、MO-01〜03 |
| G3 小額実運用 | 実投票（上限数百円） | G2 ＋ SC-06/07、WB-04、AU-01/02、MO-04、RL-01/03/05、DR-05 の 30 日連続 GREEN |
| G4 本格運用 | Kelly 1/4 | G3 ＋ 90 日の SLO 達成、DB-08、CO-06、および学習側 RF ガード未発火 |

CI 実行マトリクスは、push 時に `unit`＋`component`、PR マージ時に `integration` を追加、リリース前に `e2e`＋`costly` を実行、本番では `synthetic_monitor` を常時実行とする。失敗時のトリアージは「Blocker → 即時ロールバックまたは推論停止 → 再現フィクスチャ化 → 修正 → 当該 ID の回帰テスト追加」の順で固定し、フィクスチャ化を経ない修正はマージ不可とする。

## 12. テストで担保できない領域（リスク登録）

自動テストが守れるのは「設計どおりに動くこと」までであり、次の 3 点は別管理とする。第一に、NAR 側の仕様変更・配信停止といった外部要因は検知（DR-02/03）はできても回避はできないため、縮退運転を前提とする。第二に、賭博に関する助言・情報提供の法的位置づけ、および有料サービス化に伴う規約・表示義務は法務レビューが必要で、テスト項目としては「免責表示の存在確認」までしか担保しない。第三に、モデルの実収益性は G3/G4 の実績で事後的に判定するしかなく、テストの GREEN は収益の保証ではない。資金は生活資金と分離し、想定最大ドローダウン内で運用する方針を運用手順書側に明記しておくことを推奨する。
